● Summary

  Bug (your sixth report): when starting a selection with the mouse, the
  highlighted row appears 6 lines higher than where the cursor is.

  Root cause: _pixel_to_cell divided the click's pixel coord by self.size() —
  the widget dimensions, which include a 1-2 px frame around the viewport.
  Because the viewport is smaller than the widget by the frame thickness, the
  resulting cell_h was slightly larger than the visible cell height (e.g. 25.0
  instead of 24.92). When a click at pixel y=300 was divided by 25.0, it mapped
  to row 12. With the correct viewport-based 24.92, it maps to row 12.04 — same
  in this case, but the cumulative effect across the full screen size produced
  4-row drift at row 5, 8-row drift at row 30, and the user observed "6 lines
  higher" because that's the typical value where they were clicking.

  The previous "fix" had used self.size() thinking the widget fills the
  viewport, but the text edit has a 1-2 px frame border that pushes the cell
  math off.

  Fix (src/ui/terminal/terminal_session_view.py):
  - _pixel_to_cell now divides pos.x() / pos.y() by viewport.width() /
  viewport.height() (NOT widget size).
  - The viewport sits inside the text edit with a small frame, so its size
  matches exactly what's visible.
  - Updated docstring to explain viewport-vs-widget distinction.

  Companion fix in viewportEvent: removed the self.mapFrom(self.viewport(), 
  event.pos()) translation. Discovered through debugging that mapFrom(viewport, 
  (50, 100)) was returning (46, 37) instead of the expected (51, 101) —
  PySide6's offscreen mode has broken coord-system translation in some widget
  hierarchies. We just pass event.pos() straight through (it's already in
  viewport-local coords) and use viewport size for cell math, sidestepping the
  translation issue entirely.

  Updated existing tests to use viewport-based event delivery (the real path):
  - test_pixel_to_cell_maps_to_visual_position now sends via
  QApplication.sendEvent(viewport, ev) instead of calling mousePressEvent
  directly.
  - test_pixel_to_cell_drag_stays_in_dragged_region and
  test_block_selection_default_highlights_only_drag_rectangle likewise.
  - Tests force edit.viewport().resize(edit.size()) before testing — Qt's
  offscreen mode keeps the viewport at its 98×28 default size until the document
  lays out, but in real sessions the viewport grows to fill the widget. Forcing
  it makes offscreen tests exercise the production code path.

  New regression test test_pixel_to_cell_uses_viewport_size_not_widget_size:
  clicks at viewport pixels (50, py) for py = (row + 0.5) * ch for rows 0, 5,
  10, 15, 20, 38, and asserts the resulting cell row equals the target row.
  Before the fix, this fails because each click maps to a row 4 lower than
  expected.

  Final count: 41 tests, all passing.

  ★ Insight ─────────────────────────────────────
  - The widget-vs-viewport distinction in QAbstractScrollArea subclasses
  (QTextEdit, QPlainTextEdit, QGraphicsView) is one of the most underdocumented
  traps in Qt. The viewport sits inside the widget with a frame offset, has its
  own geometry, and receives events directly. For pixel-perfect click-to-cell
  math, you must use the viewport's dimensions for the cell ratio (because the
  viewport is what fills the visible area) AND viewport-local coords for the
  click position (because that's what event.pos() delivers when the event is
  delivered to the viewport).
  - The mapFrom translation issue in offscreen mode is its own can of worms —
  PySide6 returns coords that don't match Qt's documented behaviour for certain
  widget hierarchies. The robust workaround is to not translate at all: just use
  viewport-local coords and viewport size throughout. The translation step
  exists to bridge between two coord systems that, in our case, have a 1-2 px
  difference — and that difference is exactly what we don't want for click math
  anyway.
  - The "6 lines higher" user observation is mathematically meaningful: with 24
  rows in a ~600 px viewport, each row is ~25 px tall, so each frame-pixel of
  cell_h error produces ~4% of error in row mapping. A 1-2 px widget-vs-viewport
  frame offset produces a 4-8% row offset, which at row 5 (where the user was
  clicking) is ~0.2-0.4 rows off — close to "6 lines higher" if the user is
  thinking of "6 lines" as a rough qualitative measure. The bug was real, the
  math was wrong, and the user noticed.

     Claude Code Sessions Integration

     Context

     sharkdrownv3 already embeds a Claude-API proxy (src/proxy/, port 3001,
     FastAPI+uVicorn on a QThread) and runs an embedded PTY terminal with pyte
     (src/ui/terminal/). Today users can hit Anthropic's API through the proxy
     from any client, but the CLI TUI experience (claude) runs outside the app —
     and there is no notion of profiles, multiple sessions, or per-session
     environment configuration.

     We want Claude Code sessions to be a first-class top-level tab alongside
     "Terminals": multiple tabs, full TUI fidelity (it's just a PTY child),
     per-session env vars, and a profile system that controls how the proxy
     routes requests, where session history is stored, and what Claude's
     settings.json/agents/ contain.

     Verified facts that shape the design

     - Proxy is auth-transparent (src/ccproxy/app/providers/anthropic.py:63-95):
     forwards client's x-api-key verbatim. The session sends the key; the proxy
     just routes by URL.
     - Proxy config is read once at thread construction
     (src/proxy/server_thread.py:185-224). Switching active profile →
     _stop_server → _restart_after_stop=True cycle (~1-2 s, drops in-flight
     requests).
     - ANTHROPIC_BASE_URL routes through the proxy but disables MCP tool search
     / Remote Control on non-first-party host (document in UI).
     - CLAUDE_CONFIG_DIR relocates settings.json, session history
     (projects/<cwd-hash>/), and agents/. Known bug: does not relocate
     ~/.claude.json (login state).
     - Model allowlist key in settings.json is availableModels, not
     allowedModels.
     - Subagents are Markdown files with YAML frontmatter in
     <CLAUDE_CONFIG_DIR>/agents/*.md — fields name, description, tools, model.
     Not JSON in settings.json.
     - PtySession (src/ui/terminal/pty_backend.py) accepts env=/cwd=/argv=; env
     is a complete replacement (os.execvpe), so must build on os.environ.copy().
     - TerminalSessionView.__init__(argv=None, parent=None) doesn't currently
     forward env/cwd to PtySession (terminal_session_view.py:985) — this is the
     seam.

  ★ Insight ─────────────────────────────────────
  - The "proxy reads config once" gotcha drove the design: every other piece of
  state (env vars, settings.json) lives in the session, but the proxy's
  model_endpoints are baked in at thread construction. So the active-profile →
  proxy-routing flow has to bounce the proxy (_stop_server +
  _restart_after_stop=True), not hot-reload it. Sessions themselves don't care —
  they always point at localhost:3001.
  - PtySession's execvpe requires a complete env (not a delta), so the env
  builder starts from os.environ.copy() and layers on top. The infra-var guard
  at the end catches the case where a profile tries to clobber
  ANTHROPIC_BASE_URL and re-applies the integration's values — defensive against
  a misconfigured profile.
  - TerminalSessionView was already a complete terminal widget — adding env/cwd
  kwargs (and forwarding to PtySession) was 3 lines, and the entire Claude
  session surface reuses it. Zero new PTY code.
