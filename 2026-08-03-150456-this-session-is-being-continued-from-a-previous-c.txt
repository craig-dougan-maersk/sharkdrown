● Summary

  The bug was a stale cache in _resolve_launch_mode. The resolver cached
  shutil.which("docker") on the first call, pinning the answer to whatever PATH
  looked like at app start. Since docker wasn't installed (and never will be on
  your machine), the cache was False from the first session onwards — and
  subsequent updates to container_runtime: "podman" in global settings were
  silently ignored.

  ★ Insight ─────────────────────────────────────
  The cache was a premature optimization. shutil.which() does a stat per PATH
  entry — typically 20-50 stat calls. That's microseconds, not milliseconds.
  Caching it to avoid "slow path" calls was wrong: it traded a measurable cost
  (microseconds per call) for an unmeasurable one (zero) at the price of a real
  bug (runtime switches silently ignored).

  This is the "stale cache" anti-pattern in disguise. Caches work when the
  underlying value changes rarely AND invalidation is cheap. Here the value
  (PATH contents) can change at any moment — user installs docker, switches to
  podman, changes $PATH in their shell. And invalidation had no hook (the user
  changing settings doesn't notify the resolver). Classic stale-cache bug.

  The right fix is the simplest one: just call shutil.which() every time. The
  "performance" justification was wrong from day one.

  The pre-existing test had the bug baked in:
  test_resolve_launch_mode_falls_back_without_docker had explicit if hasattr(cv,
  "_docker_available"): delattr(cv, "_docker_available") — a tell-tale sign the
  author knew the cache caused test-ordering issues. That workaround is now
  dead code; I removed it.
  ─────────────────────────────────────────────────

     Container Env Var Propagation Fix

     Context

     When a Claude session launches inside a container
     (profile.run_in_container=True), the user reports that ANTHROPIC_BASE_URL,
     ANTHROPIC_AUTH_TOKEN, ANTHROPIC_MODEL, API_TIMEOUT_MS, and MODEL are all
     missing inside the container. Investigation found two compounding bugs that
     prevent env vars from reaching the inner claude process:

     Bug 1: ANTHROPIC_AUTH_TOKEN is never set

     src/profiles/env_builder.py:build_claude_session_env lists
     ANTHROPIC_AUTH_TOKEN in INFRA_ENV_VARS (so profile-level env vars can't
     clobber it), but never actually assigns it. The function only sets
     ANTHROPIC_API_KEY. Claude Code uses ANTHROPIC_AUTH_TOKEN (when present) for
     Authorization: Bearer auth — required by proxy gateways like MiniMax.

     Bug 2: env dict never reaches the inner container process

     DockerSession.run (src/ui/claude/docker_session.py:317) passes the env dict
     to Popen(env=self._env), which sets the env on the outer podman exec
     process. podman exec does not inherit host env vars by default — it only
     forwards vars from the container's PID 1 (image-baked env). The inner
     claude process therefore sees no SharkDrown-supplied vars at all. This is
     verified by:
     - podman run --rm --entrypoint '["env"]' alpine:latest → only PATH, HOME,
     HOSTNAME, container=podman
     - With host env vars set: ANTHROPIC_BASE_URL=… podman run … → those vars
     are NOT present in the container
     - With -e VAR=value flags: the vars ARE present

     This bug also affects ANTHROPIC_BASE_URL, ANTHROPIC_API_KEY,
     ANTHROPIC_MODEL, etc. — every "infra var" the env_builder sets. The reason
     local PTY sessions work is that PtySession calls os.execvpe with the env
     dict directly, bypassing the exec process entirely.

     Fix

     Change 1: Set ANTHROPIC_AUTH_TOKEN in build_claude_session_env

     File: src/profiles/env_builder.py

     - After the line that sets env["ANTHROPIC_API_KEY"] (~line 181), add:
     env["ANTHROPIC_AUTH_TOKEN"] = api_key if api_key else SENTINEL_API_KEY
     - Apply the same fix in the "safety net re-apply" block (~line 210) so a
     clobber attempt can't strip it.
     - The same api_key value is used for both — Claude Code prefers
     ANTHROPIC_AUTH_TOKEN over ANTHROPIC_API_KEY when both are set, so the
     Bearer auth path wins. The proxy's AnthropicProvider.forward strips any
     client-provided x-api-key and replaces it with the resolved per-provider
     key, so a duplicate header isn't a problem.

     Change 2: Pass env vars via -e flags in DockerSession.run

     File: src/ui/claude/docker_session.py

     - In DockerSession.run, build the exec command so each env var becomes a -e
     KEY=VALUE flag:
     env_args: list[str] = []
     if self._env:
         for key, value in self._env.items():
             env_args.extend(["-e", f"{key}={value}"])
     cmd = [runtime, "exec", "-i", "-t", *env_args, container, *self._argv]
     - Place the env flags between -t and the container name so the resulting
     argv matches the expected pattern: [runtime, exec, -i, -t, -e, ..., -e, 
     ..., container, ...argv].
     - Leave env=self._env in the Popen call alone — it's still useful for the
     outer podman process (e.g. for PATH-based binary resolution), and a future
     feature might surface those vars.
     - Add a docstring note explaining why -e flags are needed (podman exec
     doesn't inherit host env) so the next reader doesn't strip them as
     "redundant with env=".

     Change 3: Update existing tests

     File: tests/test_global_settings.py

     env["ANTHROPIC_AUTH_TOKEN"] == "sk-real".

  Why two stores (profiles.json + claude_global.json)? Per-profile data
  (profiles.json) and truly-global data (claude_global.json) are persisted
  separately so editing "global providers" doesn't dirty the profile JSON, and

  Why chmod 600 on everything? The credential store holds plaintext API keys
  (and possibly more in the future); the global settings file holds provider
  URLs and ports. Both are user-private data, so the codebase enforces 0o600 on

  chmod-race window. The atomic-write pattern (tempfile.mkstemp + os.replace)
  ensures readers never see a partial file.
